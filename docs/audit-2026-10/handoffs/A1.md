# A1 → other tracks (requests and things to know)

The data layer now has a shared, refcounted store (`src/data/store.ts`) behind every hook in `src/hooks/data.ts`. Hook names and return shapes are unchanged. What changed for you:

## Everyone
- `useAllGroupData()`, `useGroups()`, `useGroup()`, `useExpenses()`, `useSettlements()`, `useActivity()`, `useCaptures()`, `useInbox()` return the already-loaded value synchronously on mount (no `null` first render once the data has arrived in this session). Keep your `if (!data) return <Loading/>` guards: they still cover the very first load, but they no longer flash on a tab switch.
- Every `repo.watch*` callback now receives an optional second argument `meta: SnapMeta` (`{ fromCache, hasPendingWrites, error? }`, `src/data/repo.ts`). You don't have to use it.
- `catchUpRecurring` runs in one place now (the shared expenses listener); nothing to call from pages.
- `computeGroupData` is memoised per group in the provider; reading `useAllGroupData()` many times in one tree is free.

## C1 (ExpenseForm / expense-draft)
- `computeSplits(total, type, input, memberOrder, currency?)` has an optional 5th argument. Pass the currency being typed (`fg.currency` / `cur`) so the "Amounts add up to ₹10.00, not ₹12.00" message is formatted in it (without it the message falls back to `10.00`).
- `computeSplits` now throws `SplitError` for: negative exact amounts / item amounts / shares / percentages, non-finite numbers (`Infinity`, `NaN`), an item whose people have all left the group ("“Wine” is assigned to someone who left the group"), and a final "The split doesn’t add up to the total" invariant. Show the message inline next to the split as planned; don't pre-filter negatives silently.
- `allocate()` ignores non-finite weights and scales huge ones, so `1e308` shares no longer produce NaN; the form can still clamp shares to a sane range for UX.
- `isBalancedExpense` now rejects negative `paidBy`/`splits` entries (form already filters `> 0` payers; keep that).

## C2 (GroupForm / GroupDetail / Groups / Join)
- `repo.deleteGroup(id)` now **rejects** with a readable message when offline ("You’re offline. Connect to delete a group.") or when the server listing fails. `GroupForm.remove` (`src/pages/GroupForm.tsx` ~L226) has no try/catch: wrap it, show `errText(e)` via toast, and use `useConfirm()` instead of `window.confirm` (plan). Comments are now listed 20 expenses at a time (parallel) instead of one awaited query per expense.
- `repo.joinGroup` returns the group id at once when this device already knows the user is a member (so `Join.tsx` gets no permission error on a second tap). Keep the existing `alreadyMember` redirect: it still covers a device that hasn't cached the group.
- `useGroup(id)` keeps `undefined` = loading, `null` = not found / no access; a freshly created group still waits instead of reporting `null` (lib/fresh behaviour preserved).
- Nothing in `GroupData` changed; `group.archived` is a plain settings field, untouched by A1.

## C3 (Inbox / Capture / Scan / AutoCaptureSetup / StatementImport)
- `useCaptures()` no longer hangs forever behind a captive portal: after 5 s it reports the cached (maybe empty) list. New `useCapturesMeta()` (`src/hooks/data.ts`) returns `SnapMeta | undefined`; `meta?.fromCache === true` means "the server hasn't confirmed yet", so the Inbox can show a quiet "Checking for new captured payments…" line instead of treating an empty list as final.
- `repo.readReceiptAi()` now returns `{ unavailable: true, reason }` when the server declines (B's `src/lib/ai.ts` already handles it via `ReceiptAiResult`; `AiUnavailable` / `ReceiptAiResult` are exported from `src/data/repo.ts`). `readStatementAi()` still returns `null` when unavailable because `StatementImport` reads `r.statement` directly; if you want the reason there, switch to `if (r && 'unavailable' in r)` first and tell A1/the lead to flip the repo (one line in `firebaseRepo.readStatementAi`).
- Demo repo: `updateCapture` on a missing capture no longer throws; like Firebase it resolves and reports through `repo.onError` (toast from App). Same for purge-by-non-deleter and `bulkImport` on a missing group.
- `localRepo.getInvite` returns `null` for personal groups (Firebase never writes an invite for them).

## B (rules / functions / shared)
- `src/lib/balances.ts`: `isBalancedExpense` now requires `v >= 0` in both maps — mirror in `functions/src/lib/balances.ts` (or in the shared `balances-core.ts` you're creating). `countable()` is now pure: `countable(list) → { ok, rejected }` (no console.warn inside the lib); the hook reports `rejected` once. If you move `countable`/`isBalancedExpense` to `shared/`, keep those shapes.
- Self-leave invite write (`removeMember`): still written by the client for non-personal groups (`firebaseRepo.ts` `removeMember`). If your rule can't accept it under `getAfter`, tell A1/the lead: the change is to skip `batch.set(inviteRef…)` when `m.uid === me()` (one `if`).
- Server-side recursive delete: `deleteGroup` still deletes everything client-side. When `onGroupDeleted` exists, the client path can shrink to "delete group doc + invite" — I left the full path so the app works before your trigger is deployed; the lead can cut it to the last batch (`last.delete(inviteRef)`, `last.delete(groupRef)`) once the trigger is live.
- `saveExpense` on an edit now does `batch.update` with only the changed fields (+ `updatedAt`), `deleteField()` for removed ones, and writes `approvals` only when the money changed (whole-map replace with the editor's own key or `deleteField()`): that satisfies `trustFieldsKept` (removals only). A rules test for "edit with a stale cache keeps a concurrent approval" would be: approve as B, then update as A with only `description` changed → `approvals.B` still true.
- `watchCaptures` and the lists use `includeMetadataChanges: true`; no rules impact.
